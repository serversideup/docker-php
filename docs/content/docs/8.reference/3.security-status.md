## When and how images are scanned
A scan runs after every production publish. That covers each release, the Tuesday 08:00 UTC weekly rebuild, and the runs that ship new PHP patches. [Grype](https://github.com/anchore/grype) scans the `linux/amd64` image of every published tag, pulled from GitHub Packages.

The scan job has read-only access and no registry credentials. Grype runs in its own container. A separate job that never runs scanner code signs the results and publishes them.

Each image's results are also attached to it as a signed attestation. [Verifying images](/docs/guide/verifying-images#verify-the-vulnerability-scan) shows how to check it.

## Most findings have no fix yet
A scanner matches every package in the image against public CVE databases. Many of the CVEs it reports are ones the distribution has marked "not fixed" or "won't fix". For those, there is no newer package to install. A typical Debian image shows a large number of these. A scan of `8.5-cli-bookworm` found 18 critical and 144 high CVEs. None of them had a fix.

No rebuild can change an unfixed finding. The fixable count is the meaningful number: findings where a newer package exists. The weekly rebuild picks those up on its own. The docker-library project explains this in more depth in [Why does my security scanner show that an image has CVEs?](https://github.com/docker-library/faq#why-does-my-security-scanner-show-that-an-image-has-cves)

## Fixable findings that survive a rebuild become issues
A critical or high CVE that has a fix and shows up in two scans in a row survived a rebuild. Something is holding it back. Each one gets a public GitHub issue labeled [`security-scan`](https://github.com/serversideup/docker-php/issues?q=label%3Asecurity-scan), assigned to the maintainer.

- An issue updates in place on every scan and closes itself once a scan no longer finds the CVE.
- A scan opens at most 10 new issues. The rest wait for the next scan.

These issues track CVEs that are already public upstream. To report a problem in our own scripts, configs, or workflows, use [private vulnerability reporting](https://github.com/serversideup/docker-php/security/policy) instead.

## Read the results from your own tools
The data behind this table is public JSON on the `security-reports` branch:

```text [URL]
https://raw.githubusercontent.com/serversideup/docker-php/security-reports/reports/index.json
```

- `reports/index.json` lists every image with its counts per severity and how many of each are fixable. Its `fixable` list holds each fixable critical or high finding, with the images it affects and `consecutive_scans`, the number of scans in a row that found it.
- `reports/images/<image>.json`, such as `reports/images/8.5.12-cli-bookworm.json`, holds one image's critical, high, and medium findings. Low and negligible findings are only counted.
