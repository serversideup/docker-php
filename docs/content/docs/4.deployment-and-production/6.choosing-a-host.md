Your image runs on any host that runs Docker, so you can choose on price, location, and how much of the server you want to manage, and move later without rebuilding your app.
::

## Types of hosting

| Type | You manage | Good fit |
|------|------------|----------|
| VPS | The server, Docker, updates, and backups | Most PHP apps, on one server or a few |
| PaaS | Only your app | Teams that don't want to manage servers |
| Managed Kubernetes | Your cluster configuration | Apps that need many servers and automatic failover |

A VPS costs the least per CPU and gigabyte of memory, but you are responsible for the server. A PaaS costs more and runs your containers for you. Start with the simplest option that fits: one VPS, then Docker Swarm across a few servers as you grow, and Kubernetes only when you need many servers. Your image runs the same on all three.

## What to look for
- **Docker support.** Any Linux VPS can run Docker. On a PaaS, check that it runs your own image and lets you set environment variables and health checks.
- **Resources.** Plan on at least 1 GB of memory and one CPU, and 2 GB or more for most production apps. Leave room for PHP-FPM workers: each one can use up to `PHP_MEMORY_LIMIT` (`256M` by default). See [PHP-FPM workers](/docs/deployment-and-production/production-performance-tuning#php-fpm-workers).
- **Data center location.** Close to your users, and in the regions your data must stay in.
- **Backups.** Provided by the host or easy to run yourself. Keep at least one copy off the host.
- **Pricing you can predict.** Usage-based billing should come with alerts before you hit a limit.
- **Logs and access.** You should be able to read container logs and get a shell when something breaks.
- **No lock-in.** Prefer hosts that run standard images, so you can move.
