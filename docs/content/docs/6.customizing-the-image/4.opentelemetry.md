::lead-p
Our images ship with the [`opentelemetry`](https://github.com/open-telemetry/opentelemetry-php-instrumentation){target="_blank"} PHP extension, so you can instrument your application with distributed tracing without building a custom image or running a separate agent process.
::

## What's included (and what isn't)

The extension is **installed but inert**. On its own it does not create spans, connect to anything, or add measurable overhead. It only becomes active once your application installs the OpenTelemetry SDK via Composer.

| | Included in the image | You provide |
|---|---|---|
| `opentelemetry` PHP extension | ✅ | |
| OpenTelemetry SDK + exporters | | ✅ Composer |
| Auto-instrumentation packages | | ✅ Composer |
| `grpc` extension | ❌ (see below) | ✅ Only if you need OTLP/gRPC |

::note
The `opentelemetry` extension requires **PHP 8.0 or higher**, so it is not installed on our PHP 7.4 images. Everything on this page assumes PHP 8.0+.
::

## Why an extension instead of an agent?

Many APM tools expect you to run a vendor agent as a second process inside the container. That approach conflicts with S6 Overlay, which expects to be PID 1 in our `fpm-nginx`, `fpm-apache`, and `frankenphp` variations.

OpenTelemetry for PHP is **in-process**: it is an extension plus Composer packages. There is no second process to supervise, which sidesteps that conflict entirely. It is also vendor-neutral, so the same setup exports to Grafana, Honeycomb, Datadog, New Relic, Signoz, Jaeger, or a self-hosted OpenTelemetry Collector.

## Quick start with Laravel

### 1. Install the Composer packages

```bash [Terminal]
composer require \
  open-telemetry/sdk \
  open-telemetry/exporter-otlp \
  open-telemetry/opentelemetry-auto-laravel
```

::note
The OTLP exporter needs a PSR-18 HTTP client. Laravel already ships Guzzle, but you may also need `php-http/guzzle7-adapter` depending on your dependency versions.
::

### 2. Set your environment variables

These are the [standard OpenTelemetry variables](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/){target="_blank"}, read directly by the SDK. We deliberately **do not** set defaults for them in the image, so that your configuration is never silently overridden.

```yml [compose.yml]
services:
  php:
    image: serversideup/php:8.4-fpm-nginx
    environment:
      OTEL_PHP_AUTOLOAD_ENABLED: "true"
      OTEL_SERVICE_NAME: "my-laravel-app"
      OTEL_TRACES_EXPORTER: "otlp"
      OTEL_EXPORTER_OTLP_PROTOCOL: "http/protobuf"
      OTEL_EXPORTER_OTLP_ENDPOINT: "http://otel-collector:4318"
      OTEL_PROPAGATORS: "baggage,tracecontext"
    ports:
      - 80:8080
    volumes:
      - ./:/var/www/html

  otel-collector:
    image: otel/opentelemetry-collector-contrib:latest
    ports:
      - 4318:4318
```

That's it. Requests through your application will now produce traces, with no custom `Dockerfile` and no sidecar agent.

## Configuring the extension

Alongside the standard `OTEL_*` variables, the extension itself has a few settings that we expose using our usual environment variable convention.

| Variable | Default | What it does |
|---|---|---|
| `PHP_OPENTELEMETRY_ATTR_HOOKS_ENABLED` | `Off` | Enables the `#[WithSpan]` attribute for instrumenting functions without manual span code |
| `PHP_OPENTELEMETRY_ALLOW_STACK_EXTENSION` | `Off` | Allows multiple hooks to extend the same call stack; some instrumentation combinations require it |
| `PHP_OPENTELEMETRY_VALIDATE_HOOK_FUNCTIONS` | `On` | Validates that hooked functions exist and are hookable |
| `PHP_OPENTELEMETRY_DISPLAY_WARNINGS` | `Off` | Surfaces extension warnings, useful when spans aren't appearing |

### Using the `#[WithSpan]` attribute

Set `PHP_OPENTELEMETRY_ATTR_HOOKS_ENABLED=On`, then annotate any method:

```php [app/Services/ReportService.php]
use OpenTelemetry\API\Instrumentation\WithSpan;

class ReportService
{
    #[WithSpan]
    public function generateMonthlyReport(int $month): Report
    {
        // This method now appears as its own span in your traces
    }
}
```

## What about gRPC?

We do **not** include the `grpc` extension, because OTLP over HTTP (`http/protobuf`) does not need it and gRPC is by far the most expensive piece to bundle. In our testing, adding `grpc` grows an Alpine image by roughly 15%, while the `opentelemetry` extension itself costs well under a megabyte.

If you specifically need OTLP over gRPC, add it in your own `Dockerfile`:

```dockerfile [Dockerfile]
FROM serversideup/php:8.4-fpm-nginx

USER root
RUN install-php-extensions grpc
USER www-data
```

::tip
For most setups `http/protobuf` is the better default anyway — it is simpler to route through proxies and load balancers, and the OpenTelemetry Collector accepts it on port `4318`.
::

## Verifying the extension is active

```bash [Terminal]
docker run --rm serversideup/php:8.4-cli php --ri opentelemetry
```

You should see the extension version and its current directive values. To confirm an environment variable took effect:

```bash [Terminal]
docker run --rm -e PHP_OPENTELEMETRY_ATTR_HOOKS_ENABLED=On \
  serversideup/php:8.4-cli php --ri opentelemetry | grep attr_hooks_enabled
```

## Troubleshooting

**No spans are appearing.** Confirm `OTEL_PHP_AUTOLOAD_ENABLED=true` is set — without it the SDK never registers, even with the extension loaded and the packages installed.

**Still nothing.** Set `PHP_OPENTELEMETRY_DISPLAY_WARNINGS=On` to surface warnings from the extension about hooks that failed to attach.

**Connection errors to the collector.** Check that `OTEL_EXPORTER_OTLP_ENDPOINT` points at the OTLP/HTTP port (`4318`), not the gRPC port (`4317`), when using `http/protobuf`.
